# 功能测试方法论（黑盒为主，白盒补盲）

目标：把一个「验证需求/版本是否正常」的模糊请求，收敛成**可复跑**的用例、**结构化**的证据、**可归因**的报告。

本 skill 负责「测什么、期望是什么、失败算谁的」；执行交给工具：`ft_http_run`（接口）、`ft_ui_run`（页面）、`ft_report`（报告）。

## 0. 唤起与开场确认（按顺序执行，不要跳步）

触发：用户说「开始测试」，或明确要求测试接口/页面/功能。

1. **确认项目**：问清这轮要测哪个项目（项目名/仓库/服务）。用户已经指明就跳过。
2. **确认测试类型**（让用户三选一）：
   - **单测接口**：只测 HTTP 接口，不驱动页面。
   - **单测页面**：只做 UI 自动化，不校验接口契约。
   - **测模块功能**：接口 + UI 页面 + **前后端一致性**（同一数据下，UI 展示与接口返回的字段、口径、单位、分页/排序、错误提示是否一致）。
3. **提醒用户给入口**：请用户发送接口地址（测试环境 `baseUrl`、接口路径或 Controller/接口文档）或 UI 所在路由（如 `/user/list`，或完整 URL）；同时确认环境、账号/凭据方式（凭据只走环境变量）。代码不在当前工作区时，要项目路径。
4. **查登录档案**：先看 `.ft/logins/<project>.json`（见 §1）。已有档案 → 本轮默认「登录 + 本轮功能」联合测试，并告诉用户会先跑一次登录；没有档案但接口需要令牌 → 按 §1.2 向用户索要登录接口，**不要猜登录路径**。
5. **定位代码接口定义**（只读，不改项目代码）：
   - 后端：`@RestController`/`@RequestMapping`/`@GetMapping` 等路由、参数 DTO 与 `@Valid` 校验、Service 分支、全局异常处理、统一返回体与错误码。
   - 前端：路由表、页面组件、API 调用层（axios/请求函数）、表单校验与错误提示。
   - 产出「接口契约清单」+「关键分支清单」，作为用例设计依据。找不到代码就要求仓库路径或接口文档，**不要猜契约**。
6. **确认多接口执行逻辑（涉及 2 个及以上接口时必做，禁止过度猜测）**：用 `ask_user_question` 选择题问清，按用户答复记录，**不要从代码结构自行推断调用链、依赖关系或执行顺序**：
   - 执行方式：**顺序**（有依赖，前一个的返回给后一个）/ **分支**（按条件走不同路径）/ **并行**（互不依赖、顺序无关）；
   - 具体顺序：先调哪个、后调哪个；依赖关系（A 的哪个字段传给 B 的哪里）；分支条件由谁触发、各自准备什么数据；
   - 执行器现状要如实说明：v1 固定串行（`concurrency` 只能 1），并行诉求按确认的顺序串行跑；运行时条件分支不支持，拆成多条用例或多次 run 覆盖；
   - 模块功能测试（接口 + UI）也要确认先后：先接口后 UI、还是先 UI 再回查接口作为对照（前后端一致性通常用同一数据交叉验证）；
   - 用户答复不明确就继续问，确认后写进数据确认卡的「执行逻辑」一栏，再准备测试数据。
7. **准备测试数据，并发给用户确认**：按 `references/round-record.md` 的「数据确认卡」输出（环境、凭据来源、前置数据、本轮将创建/修改的数据、清理方式、是否放行写操作、执行逻辑），**等用户确认符合预期后再执行**。有登录档案的项目，确认卡里注明「本轮会先跑登录用例 LOGIN-001（计入用例总数）」，并确认登录接口的写操作已放行。
   - 例外：**UI 自动化不需要确认数据**，只要在开跑前告知本轮包含的项目（页面/路由、流程、关键动作与断言点、是否截图、登录态方式）。
8. **执行**：先跑 3~5 条冒烟确认环境通，再跑全量；一次 run 一个主题（冒烟/回归/某模块）。
9. **记录本轮档案并报告**：每轮必须记录四件事（见 §2），报告与最终回复都要能回答这四件事。

## 1. 需要登录的项目：登录档案与每轮联合测试

登录接口测过一次后要**按项目记住**，后续每轮默认复用，等于一条小型接口自动化链路；有登录的项目，每轮都会多测一次登录。

### 1.1 登录档案

- 位置：`.ft/logins/<project>.json`（项目级；环境不同用 `environments` 区分）
- 内容：登录接口（method/path/headers/body）、令牌提取路径、鉴权头格式、凭据环境变量名、期望断言、探测记录；若测过注册/验证码等前置接口也一并记录。
- 只记录**变量名**，绝不落明文凭据；模板见 `references/login-record.md`。
- 档案是下一轮联合套件的输入：每轮读取档案 → 生成「登录用例 + 本轮功能用例」一次跑完。

### 1.2 没有档案、但接口需要令牌时

不要过度推测、不要猜登录路径、不要遍历常见路径（避免触发风控/锁号）。直接：

1. 向用户索要登录/注册相关接口（method + path；有接口文档/Controller 更好）。
2. 若代码在工作区，先只读定位登录接口定义与参数 DTO。
3. 探测参数（尽量少请求）：先发缺字段/空 body 的请求观察必填项与错误结构，再成功登录一次；记录状态码、错误码、返回体结构与令牌位置。
4. 把「登录接口 + 参数 + 令牌路径 + 鉴权头格式 + 凭据环境变量名」整理后**发给用户确认**，确认后写入登录档案。
5. 从这一轮起按 §1.3 联合测试，并把登录用例计入本轮。

### 1.3 每轮联合测试（有登录的项目默认这样跑）

- 一次 `ft_http_run` 里：`LOGIN-001` 登录（`extract` 取令牌）→ 后续功能用例用 `${accessToken}` 放到鉴权头。
- 登录用例算本轮测试项：概要里要能看到它通过/失败。
- 凭据只从环境变量取：登录 body 写 `${env:FT_USERNAME}` / `${env:FT_PASSWORD}`，凭据变量名记在档案里。
- 登录失败（401/403、令牌为空）时，后续用例的鉴权失败一律按**环境/凭据问题**归因，不判产品缺陷；先修登录再跑功能。
- 令牌只在内存里传递，日志/证据/套件落盘时按敏感键脱敏（`authorization`、`password`、`token` 等）。

## 2. 每轮测试档案（强制记录）

每一轮黑盒测试都要留下以下四项，模板见 `references/round-record.md`；工具返回 `runId` 后写入 `.ft/runs/<runId>/plan.md`，并在报告/回复中引用。

| 项目 | 必须写清 | 反例 |
|---|---|---|
| **测试目标** | 这轮要验证/回答什么（需求点、验收标准、回归范围） | 「测一下用户模块」 |
| **覆盖范围** | 涉及的模块/接口/页面路由清单；明确**不覆盖**什么 | 只写「全量测试」 |
| **测试数据** | 环境、账号与凭据来源（变量名）、前置数据、构造的数据、清理方式 | 只写「用测试账号」 |
| **异常复现方式** | 失败项的前置条件 + 最小请求（method/URL/headers/body）或 UI 步骤 + 期望 vs 实际 + 证据路径 + 复跑方式 | 「有个接口报错了」 |

失败项的复现方式至少包含：前置条件、请求或 UI 步骤、期望与实际、证据（`results.jsonl#<caseId>` / 截图路径）、复跑命令（`suite.json` 路径或 `runId`）。

## 3. 六步 SOP

### S1 明确范围，按风险排序
核心链路 > 边界条件 > 异常/错误码 > 权限与越权 > 幂等与并发。
先列清单再写用例；不要一上来铺满所有字段组合。

### S2 白盒摸底（只读代码，不执行）
- 后端 Java：Controller 路由与参数校验（`@Valid`/自定义校验）、Service 分支、事务边界、全局异常处理、DTO 字段约束与序列化
- 前端 Vue：路由表、页面组件、API 调用层、表单校验规则、错误提示
- 既有测试与接口文档：契约以哪个为准，冲突时记录

产出「接口契约清单」+「关键分支清单」：每个分支至少对应一条黑盒用例。

### S3 设计用例
按 `references/api-checklist.md` 与 `references/ui-checklist.md` 的清单逐项取舍。
每条用例必须写清：输入、期望、前置数据、是否破坏性、失败时怎么判断。
多接口场景：执行方式与顺序只能用**用户确认过**的信息，不许自行推断调用链；依赖用「case 顺序 + `extract` + `${var}`」表达。

### S4 执行
- 先跑 3~5 条冒烟用例确认环境通（HTTP 200/页面能打开），再跑全量
- 有登录档案的项目：登录用例放在第一条，令牌用 `${accessToken}` 传给后续用例
- 多接口：`cases` 数组顺序就是执行顺序，按用户确认的顺序排；分支拆成独立用例，并行诉求在 v1 下按串行执行并如实说明
- 套件交给 `ft_http_run` / `ft_ui_run`；一次 run 一个主题（冒烟/回归/某模块）
- 失败不要立刻重跑全部；先看 `results.jsonl` 的 `errorKind` 和断言明细

### S5 判定与归因
按下面的规则表判断，证据不足就补证据，不要直接报 bug。

| 现象 | 初判 | 必须补充的证据 |
|---|---|---|
| 状态码/字段与契约不符 | 产品缺陷 | 契约原文 + 实际响应 + 最小复现请求 |
| 400/500 但无错误码/无提示 | 契约缺失或产品缺陷 | 接口文档、同类接口对比 |
| 环境连不上、数据被污染、登录失效 | 环境问题 | 健康检查、前置数据、重试结果 |
| 登录用例失败后其他用例 401/403 | 环境/凭据问题 | 登录用例的实际响应、凭据变量、档案 |
| 期望本身写错、断言过严（如延迟） | 用例缺陷 | 修正期望并重跑 |
| UI 元素找不到但页面正常 | 用例缺陷（选择器/等待） | 截图 + DOM 片段 + 是否有动画/懒加载 |
| UI 展示与接口返回不一致 | 产品缺陷或契约缺失 | 同一数据的接口响应 + 页面截图 + 字段对照 |

### S6 报告与沉淀
- `ft_report` 生成 `report.md`；多次 run 用 `runIds` 汇总
- 报告必须包含 §2 的四项档案 + 范围、环境、通过率、失败清单（含复现）、遗留风险
- 通过的套件保留在 `.ft/runs/<runId>/suite.json`，作为下次回归的输入
- 登录档案留在 `.ft/logins/<project>.json`，不要每轮重问

## 4. 套件最小示例

```json
{
  "schemaVersion": 1,
  "defaults": { "baseUrl": "http://127.0.0.1:8080", "headers": { "Content-Type": "application/json" } },
  "cases": [
    {
      "id": "TC-001",
      "name": "创建用户-正常",
      "destructive": true,
      "request": { "method": "POST", "path": "/api/users", "body": { "name": "张三", "age": 20 } },
      "expect": { "status": [200, 201], "jsonPath": [{ "path": "$.code", "op": "equals", "value": 0 }] },
      "extract": { "userId": "$.data.id" }
    },
    {
      "id": "TC-002",
      "name": "查询刚创建的用户",
      "destructive": false,
      "request": { "method": "GET", "path": "/api/users/${userId}" },
      "expect": { "status": 200, "jsonPath": [{ "path": "$.data.name", "op": "equals", "value": "张三" }] }
    }
  ]
}
```

写操作必须 `destructive: true`，且命中 `.ft/config.json` 的 `destructive.rules`，否则会被策略拦截（这是预期行为，不是工具故障）。登录接口也是 POST，记得把登录路径加进白名单。

## 5. 断言边界

- `status` 可以是数组（200/201 任一）
- `jsonPath` 只支持点与下标（`$.data.items[0].id`），不支持过滤表达式
- `latencyMs` 默认只告警不判失败；本机/CI 抖动大，除非明确要求，否则不要开 `strict`
- 响应体超过 1MB 会被截断，长列表断言请用 `length`/抽样字段，不要整段 `equals`

## 6. 报告要求

按 `references/report-template.md`。报告是给不看聊天记录的人看的：
- 说清「测了什么、环境是什么、一共多少条、通过率」
- 失败要说清「哪条、期望什么、实际什么、怎么复现、证据在哪」
- 结论区分：产品缺陷 / 用例缺陷 / 环境问题 / 已知问题
- 有登录的项目：报告注明登录用例是否通过，以及令牌获取方式（不写令牌值）

## 7. 安全红线

- 不测生产环境；需要写操作时先确认是测试环境
- **凭据解析顺序**：宿主环境变量 → `.ft/credentials.local.json`（工作区本地、已 gitignore）。内部系统不能注册账号时，可按用户提供的**测试/开发环境**账号写入本地凭据库；生产环境账号一律不存、不用
- suite 里只写 `${env:NAME}`，登录档案只存变量名；不要在回复里复述凭据值，不写进套件、报告、截图
- 用户发来账号密码时：先确认是测试/开发环境 → 合并写入本地凭据库 → 回复只说「已存储，变量名 XXX」；提醒聊天记录里可能留有明文，必要时轮换
- 破坏性操作用测试专用数据；能清理就清理，清理同样受 `destructive.rules` 约束
- 截图可能包含个人信息，报告里注明存放位置
